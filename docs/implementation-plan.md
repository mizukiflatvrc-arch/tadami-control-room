# 実装計画

> β0.3 / 01a 更新：Prometheus / Node Exporter は tadami で実機配備・監査済み（ユーザー報告）。Web / API の本番コンテナ構成と API 固定ビルドを himekami で実装。Web の Docker 起動・実機接続は未実施。[本番配備手順](production-web.md)、[検証記録](verification-beta-0.3-01a.md) を参照。以下の初期設計・β0.1/β0.2 の記述は経緯として保持する。

> β0.1 の状況：段階 1〜3 を実装し、段階 4 の型検査・lint・テスト・ビルド・画面確認を実施済み。連続更新は仮想時計で 1 時間分を検証し、実時間の長時間試運転は残している。検証結果と未確認事項は [verification.md](verification.md) を参照。以下の段階定義は初期計画を保持している。

## 段階 0：設計（今回）

実施内容：要件、画面配置、データ契約、モックから実データへの境界、ディレクトリ構造、実装順序を文書化する。

完了条件：

- CPU・メモリ・ストレージ・稼働時間・サービス状態の定義がある。
- 1280×1024・5:4、日本語、白背景・黒文字・細い罫線の設計がある。
- モックと実機の情報を区別し、取得不能・遅延時の表示方針がある。
- 成果物をローカル文書に限定し、サーバー設定を変更していない。

## 段階 1：作業用 PC でアプリの土台を作る

1. 作業用 PC の Node.js・npm と対象ブラウザーを確認する。
2. React + TypeScript + Vite を初期化し、互換性を確認した依存バージョンを固定する。
3. 開発・ビルド・型検査・lint 用のコマンドを用意する。
4. CSS トークン、画面外枠、見出し、罫線、日本語表示を作る。
5. 開発サーバーはローカルのループバックで起動する。

完了条件：作業用 PC で起動・ビルドでき、1280×1024 に白黒の総合監視画面の枠が表示される。本番接続の設定を要求しない。

## 段階 2：データ契約とモックを実装する

1. MonitoringSnapshot、Provider、単位変換、容量計算を定義する。
2. 架空のホスト仕様・ストレージ・サービスを fixture にする。
3. 固定シード・時計・正常時の履歴を実装する。
4. 異常・欠損・取得失敗・更新遅延・復旧のシナリオを実装する。
5. 使用率の境界、ゼロ容量、欠損、未来時刻など無効な入力の扱いを検証する。

完了条件：同じシード・時刻で同じデータが得られる。モックは容量・時系列の整合性を保ち、Provider から実機への通信が発生しない。

## 段階 3：5 種類の監視表示を実装する

1. CPU とメモリの数値・折れ線グラフを作る。
2. ストレージ表、稼働時間、サービス状態一覧を作る。
3. 状態ラベル、総合判定、観測時刻、模擬データ表示を組み込む。
4. 5 秒更新、3 秒タイムアウト、手動再取得、取消、タブ復帰時の再取得を実装する。
5. 前回値の保持、部分欠損、更新遅延、欠損区間をつながないグラフを実装する。

完了条件：5 指標が表示され、異常・取得不能・復旧をモックで再現できる。取得失敗で数値が 0 に置換されたり、モック以外の情報として表示されたりしない。

## 段階 4：モック版を検証する

| 検証 | 確認内容 |
| --- | --- |
| 基準画面 | 1280×1024、拡大率 100%、通常件数で主要情報が一画面に収まる |
| ブラウザー枠 | 1280×900 でも主要情報が読み取れ、表示が欠けない |
| 拡大・狭幅 | 200% 拡大、幅 768px で自然に縦へ流れ、操作や内容が隠れない |
| 長い値・多い行 | 長いサービス名・マウント先、ストレージ 10 行、サービス 20 行でも欠落しない |
| 判定 | 閾値直前・一致・直後、期待停止、部分不明、異常と欠損の併存 |
| 取得 | 初回失敗、連続失敗、遅い応答、タイムアウト後の復旧、要求の重複防止 |
| 鮮度 | 新しい API 応答に古い観測値が含まれても正常な鮮度と判定しない |
| 履歴 | 欠損区間が切れており、現在値だけ有効な場合にも表示できる |
| 操作性 | キーボード操作、フォーカス、見出し構造、表の列見出し、色なしでの状態識別 |
| 継続表示 | 1 時間の試運転で DOM・保持履歴・タイマーが増え続けず、時刻と更新が継続する |

自動検証は、計算と判定の単体テスト、Provider と更新処理の結合テスト、主要シナリオのブラウザーテストに絞る。デザインは実際のスクリーンショットでも確認する。ポーリングごとに読み上げが発生しないよう、状態変化の通知だけを支援技術へ伝える。

完了条件：型検査・lint・テスト・本番ビルドが成功し、基準画面と異常シナリオの表示を確認済み。README に起動方法・シナリオ切替・確認結果が記載され、モック版としてレビューできる。

## 段階 5：実データ接続の調査と設計（後続）

モック版が固まった後で、実機の読み取り調査の範囲を決める。今回この調査は実行しない。

確認項目：

- 実際の CPU・メモリ容量、マウント先、対象サービスと期待状態。
- Prometheus/Grafana/exporter の有無、バージョン、接続先、認証、scrape 間隔。
- メトリクスの実サンプルとラベル、サービス状態を取得できる方法。
- Web サーバー、ポート使用状況、配信経路、アクセス制御、本体ブラウザー。

取得済みサンプルからクエリとマッピングを決め、読み取り専用 API と ApiProvider を作業用 PC で実装する。サービス名・マウント先は対象一覧に明示する。接続試験は対象とアクセス範囲が確定してから行う。

完了条件：実機由来の応答に対する契約テストが通り、UI を書き直さず Provider を差し替えられる。必要な設定変更、影響範囲、配備方法が具体化している。

## 段階 6：本番配備（別途扱う）

既存構成に合わせて静的 UI と API の配備方法を決める。既存設定の変更が必要な場合は、対象ファイル・変更差分・影響・復旧手順を先に用意し、本番変更の指示を受けてから実行する。

本番完了条件は、実機の 1280×1024 モニターでの表示、各指標と計測元との一致、取得不能と復旧、本番データの明示、既存サービスへの影響がないこと、以前の状態へ戻せることの確認とする。

## 今回行わない操作

SSH 接続、サーバーパッケージ導入、Prometheus/Grafana/exporter 設定変更、systemd 操作、ファイアウォール変更、コンテナー起動、ポート公開、DNS/TLS 設定、デプロイは行わない。

次の着手範囲は段階 1〜4 のモック版。実機について不明な情報はモックで代替できるため、サーバー構成の確定を待たずにローカル実装を進められる。
