# アプリケーション設計

## 1. 目的と範囲

`tadami` の状態を本体モニターで常時把握できる、読み取り専用の監視画面を作る。主要な数値、異常、データの鮮度を一目で判断できることを優先する。

初期版の対象は単一ホストの CPU・メモリ・ストレージ・稼働時間・サービス状態とする。サービス再起動、シェル実行、設定編集、通知配信、複数ホスト管理、長期ログ検索は対象外。最初は完全なモックデータで実装し、本番への通信を必要としない。

実機の OS 情報はユーザー指定の Ubuntu 24.04.5 LTS を前提とする。ディスク構成、CPU コア数、メモリ容量、サービス名、監視基盤の導入状況は未確認。モック内の情報を実機情報として扱わない。

## 2. 技術構成案

| 層 | 採用案 | 理由 |
| --- | --- | --- |
| UI | React + TypeScript | 監視パネルを分割し、共通のデータ型で表示を管理する |
| 開発・ビルド | Vite | ローカル開発と静的ファイル生成を小さく始める |
| スタイル | CSS、CSS Custom Properties、Grid | 白黒の罫線 UI と 5:4 向け配置を直接制御する |
| 小型グラフ | SVG | 単色の折れ線と目盛りだけを必要最小限で描画する |
| 状態管理 | React 標準機能と取得用フック | 単一画面のため追加の状態管理ライブラリを持たない |
| 検証 | Vitest、React Testing Library、Playwright | 計算・状態遷移・実ブラウザーの表示を確認する |
| 将来の接続 API | Node.js + TypeScript の薄い読み取り専用 API | Prometheus 接続先・認証情報・クエリをサーバー側に置く |

各パッケージと Node.js のバージョンは実装開始時に互換性を確認して固定し、ロックファイルを管理する。今回はインストールしない。初期版に SSR、データベース、Docker、外部フォント配信は不要。

## 3. 監視基盤と独立 UI の関係

初期版：

```text
作業用 PC
  ブラウザー → React UI → MonitoringProvider → MockProvider
                                                └─ 固定シードのシナリオ
```

将来の接続構成案（未構築）：

```text
tadami の計測元 → Prometheus ← Grafana（詳細分析）
                       ↑
               読み取り専用 API
                       ↑ 同一オリジン /api/monitoring/snapshot
               TADAMI CONTROL ROOM
```

Prometheus を数値・時系列の取得元、Grafana を詳細分析の画面とする。CONTROL ROOM の描画やデータ取得は Grafana の埋め込みに依存させない。将来、設定済みの場合だけ Grafana の詳細画面へのリンクを表示する。

Prometheus の現在値取得には `/api/v1/query`、履歴取得には `/api/v1/query_range` を使う想定。[Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/)

ブラウザーから Prometheus に直接接続させず、API で対象ホスト・クエリ・期間・返却系列数を限定する。接続先 URL、認証情報、任意の PromQL をブラウザー入力として受け付けない。ブラウザー向け環境変数にも秘密情報を入れない。本番のアクセス制御と配信方法は既存構成を確認してから決める。[Prometheus security model](https://prometheus.io/docs/operating/security/)

## 4. 画面構成

主画面は「総合監視」一画面。常時監視のため主要情報を上から順に置き、装飾用サイドバーは設けない。

```text
┌────────────────────────────────────────────────────────────────┐
│ TADAMI CONTROL ROOM                     総合監視 / 端末 01     │
│ 対象: tadami   Ubuntu 24.04.5 LTS        現在時刻: YYYY/MM/DD … │
├────────────────────────────────────────────────────────────────┤
│ 模擬データ / 総合判定: 正常              最終取得: HH:mm:ss     │
├────────────────────────────────┬───────────────────────────────┤
│ 01 CPU                         │ 02 メモリ                     │
│ 使用率 18.4 %                  │ 使用率 42.0 %                 │
│ 過去 15 分の折れ線             │ 使用量 / 総容量               │
│                                │ 過去 15 分の折れ線            │
├────────────────────────────────┴───────────────────────────────┤
│ 03 ストレージ                                                  │
│ マウント先      使用量 / 総容量      利用可能量   使用率   判定 │
│ /               ……                  ……            ……     正常 │
│ /srv/data       ……                  ……            ……     正常 │
├────────────────────────────────┬───────────────────────────────┤
│ 04 稼働時間                    │ 05 サービス状態               │
│ 12 日 08 時間 32 分            │ サービス名    状態    確認時刻│
│ 起動日時: YYYY/MM/DD HH:mm:ss   │ ……           稼働中  ……      │
├────────────────────────────────┴───────────────────────────────┤
│ 更新間隔: 5 秒   時刻: JST   データ: 模擬         [再取得]      │
└────────────────────────────────────────────────────────────────┘
```

図中の値・ディスク・サービスはすべて架空。日本語は省略せず、必要な単位を数値と併記する。

### 寸法とレスポンシブ

- 基準はブラウザー表示領域 1280×1024、拡大率 100%。外周 24px、区画間 12px、区画内 16px を基準とする。
- 通常データ（ストレージ 3 行以内、サービス 6 行以内）で主要情報を一画面に収める。ブラウザーのツールバーを考慮し、1280×900 の表示領域でも確認する。
- 高さの目安はヘッダー 80px、状態帯 40px、CPU・メモリ 210px、ストレージ 190px、下段 210px、フッター 32px。外周・間隔を含めて約 870px に収める。
- 幅 1000px 未満で二列を一列に変更する。狭い画面・拡大表示・データ行増加ではページを縦に伸ばす。固定高さや `overflow: hidden` で情報を隠さない。
- 長いマウント先・サービス名は折り返す。ストレージの行が増えた場合もページ全体でスクロールし、表の中に小さなスクロール領域を作らない。

### 表現ルール

| 要素 | 規則 |
| --- | --- |
| 背景・文字 | 背景 `#ffffff`、主文字 `#111111`、補助文字 `#444444` |
| 罫線 | 原則 1px の `#555555`。区画番号と見出しで情報階層を作る |
| 装飾 | 角丸・影・グラデーションは使わない。通常表示の背景は白 |
| 本文 | 日本語対応のシステムフォント、基本 16px、補助情報 14px 以上 |
| 数値 | 等幅フォントまたは等幅数字、大きな指標は 32〜40px |
| 状態 | 「正常」「注意」「異常」「不明」を文字と記号で明示。色に依存しない |
| 強調 | 注意は太字と記号、異常は黒地に白文字の小さな状態ラベル |
| グラフ | 黒い細線、0〜100% の固定軸、時刻目盛り、直近値を数値でも表示 |
| 操作 | 日本語のボタン名、明瞭なキーボードフォーカス、点滅・自動演出なし |

外部 CDN・Web フォントへの依存を避け、家庭内ネットワークだけでも表示を保つ。1990 年代らしさは区画番号・整列・罫線で表現し、可読性を落とす走査線や極端な小文字は使わない。

## 5. 表示指標の定義

| 指標 | 定義 | 表示 |
| --- | --- | --- |
| CPU | 全論理 CPU の平均使用率。idle 以外の割合 | 小数 1 桁の %、過去 15 分の推移 |
| メモリ | 使用量 = 総容量 − 利用可能量。キャッシュ込みの単純な空き容量との差分にしない | %、使用量 / 総容量（GiB）、15 分の推移 |
| ストレージ | ファイルシステム単位。使用量 = size − free、利用可能量 = avail、使用率 = used / size | マウント先、GiB、%、判定 |
| 稼働時間 | 観測時点のホスト時刻 − 起動時刻 | 日・時間・分、起動日時 |
| サービス | 監視対象一覧と、各対象の稼働を示す観測結果 | 稼働中・停止・異常・不明、確認時刻 |

容量は 1024 基数、内部では bytes。ストレージの予約領域により「使用量 + 利用可能量」と総容量が一致しない場合がある。物理ディスクの健康状態・SMART・I/O 性能は初期対象外。擬似ファイルシステムや重複マウントの除外は実機構成を確認して設定する。

時刻は内部では UTC の ISO 8601、画面では `Asia/Tokyo` の日本語形式（JST）に統一する。現在時刻と最終取得・観測時刻は別物として扱う。

### 将来の計測元

Linux のホスト計測には Node Exporter が候補になるが、インストール済みとは仮定しない。[Node Exporter guide](https://prometheus.io/docs/guides/node-exporter/)

CPU・メモリ・ファイルシステム・起動時刻の実際の系列名とラベルは、接続段階で取得可能なメトリクスを読んで確定する。CPU の率計算窓は暫定 1 分とし、実際の scrape 間隔に応じて十分なサンプル数が取れる長さへ調整する。

サービスの監視方式は systemd unit、コンテナー、HTTP ヘルスチェックなどから実機に合わせて選ぶ。Prometheus の `up` はスクレイプの成否を表すため、個々のアプリケーションの稼働状態にそのまま転用しない。観測方法が未設定のサービスは「不明」とする。[Prometheus jobs and instances](https://prometheus.io/docs/concepts/jobs_instances/)

## 6. データ契約

画面は Prometheus のレスポンス形式を直接扱わず、共通の `MonitoringSnapshot` を受け取る。初期は MockProvider、将来は HTTP 経由の ApiProvider が同じ契約を実装する。

以下は型の設計案であり、今回コードは実装しない。

```ts
type Quality = 'fresh' | 'stale' | 'unavailable';
type Health = 'normal' | 'warning' | 'critical' | 'unknown';
type ServiceState = 'running' | 'stopped' | 'failed' | 'unknown';

type Observation<T> = {
  value: T | null;
  observedAt: string | null; // 元データを観測した時刻。再取得時刻で上書きしない
  quality: Quality;
  reason: string | null;
};

type HistoryPoint = { at: string; value: number | null };
type Filesystem = {
  id: string;
  mountpoint: string;
  capacity: Observation<{
    totalBytes: number;
    freeBytes: number;
    availableBytes: number;
  }>;
};

type MonitoringSnapshot = {
  schemaVersion: 1;
  source: 'mock' | 'prometheus';
  host: { id: string; name: string; osLabel: string };
  fetchedAt: string; // Provider が最後に取得に成功した時刻
  cpu: Observation<{ usagePercent: number }>;
  memory: Observation<{ totalBytes: number; availableBytes: number }>;
  filesystems: Filesystem[];
  uptime: Observation<{ seconds: number; bootedAt: string }>;
  services: Array<{
    id: string;
    name: string;
    expectedState: 'running' | 'stopped';
    state: Observation<ServiceState>;
  }>;
  history: { cpu: HistoryPoint[]; memory: HistoryPoint[] };
};

interface MonitoringProvider {
  getSnapshot(signal: AbortSignal): Promise<MonitoringSnapshot>;
}
```

監視対象のストレージ・サービス一覧は設定側で保持し、データが欠けても行ごと消さない。観測値を `null` として「不明」を示す。API 応答は実行時にも型・範囲・有限数・時刻を検証し、ゼロ除算や `NaN`、不正な容量関係を欠損として扱う。

履歴は過去 15 分、15 秒間隔（両端を含めて最大 61 点）を初期仕様とする。欠損区間は線を切り、正常値で補間しない。履歴だけ欠損しても現在値が有効なら現在値を表示する。

## 7. 更新・判定・取得失敗

- 初回は「取得中」。取得成功後に 5 秒間隔で更新する。前の要求が完了するまで次を重ねない。
- 一回の取得タイムアウトは暫定 3 秒。画面破棄時は AbortSignal で中止する。
- 手動の「再取得」は自動更新と同じ処理を使い、取得中は重複操作を抑止する。
- バックグラウンドのタブでは自動更新を休止し、復帰時に再取得する。
- 失敗時は取得失敗を直ちに表示し、最終成功値とその時刻を保持する。値を 0 や正常状態に置き換えない。
- 観測時刻から暫定 30 秒を超えた値は「更新遅延」。取得した時刻が新しくても元データが古ければ遅延扱いとする。本番では scrape 間隔を確認して閾値を調整する。
- 一度も取得できていない値は `—` と「取得不能」。部分欠損はパネルごとに示す。
- 稼働時間は観測値として表示する。データ停止中にローカル時計だけで増やし続けない。

負荷判定とデータ品質は別に持つ。初期の暫定判定値は次の通りであり、Prometheus のアラート設定には反映しない。

| 対象 | 正常 | 注意 | 異常 |
| --- | --- | --- | --- |
| CPU | 80% 未満 | 80% 以上、95% 未満 | 95% 以上 |
| メモリ | 80% 未満 | 80% 以上、95% 未満 | 95% 以上 |
| ストレージ | 80% 未満 | 80% 以上、90% 未満 | 90% 以上 |
| サービス | 期待状態と一致 | 期待稼働だが停止 | failed、または期待停止に反する稼働 |

現在のスナップショットによる表示判定とし、継続時間を条件とする通知は後続範囲とする。稼働時間そのものには正常・異常の閾値を設けない。

総合判定は新鮮なデータの異常を優先する。異常があれば「異常」、異常がなく欠損・更新遅延があれば「不明」、すべて新鮮で注意があれば「注意」、すべて正常なら「正常」とする。異常と欠損が共存する場合は「異常 / 一部取得不能」と併記する。古い値の判定は「前回の判定」として区別し、現在正常とは断定しない。

## 8. モック仕様

モックモードではヘッダーとフッターに「模擬データ」と常時表示する。CPU コア数・容量・サービス名などは架空の fixture として定義する。

正常、CPU 高負荷、メモリ逼迫、ストレージ逼迫、サービス停止、サービス異常、部分欠損、全取得失敗、更新遅延、復旧のシナリオを用意する。開発時だけ利用するシナリオ選択機能を設ける。

固定シードと差し替え可能な時計で同じ挙動を再現できるようにする。時系列の範囲・容量の整合性を保ち、再描画のたびに乱数が変わる実装を避ける。通信遅延と失敗も Provider 層で模擬し、画面内の特例分岐にしない。

## 9. 本番移行前に決める事項

実機のブラウザーと表示領域、既存 Web 配信方式、アクセス範囲、Prometheus/Grafana の接続先・認証方式、scrape 間隔、対象メトリクス、マウント一覧、期待するサービス状態を確認する。

実データモードへの切替は明示的な設定とし、取得失敗時にモックへ自動フォールバックしない。本番配備や exporter 導入など、既存設定に変更が必要な作業は変更案と復旧方法を用意した後に別途扱う。今回の設計作業では実機にアクセスしない。
